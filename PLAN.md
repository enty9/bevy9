# План разработки игрового движка на базе Bevy (`bevy9`)

## 1. Контекст репозитория и зафиксированные решения

### База репозитория

- **Исходная кодовая база:** форк Bevy `0.20.0-dev` (Rust edition `2024`, MSRV `1.96.0`, `wgpu 30`) в репозитории `/home/enty/Projects/bevy9`.
- **Текущая ветка разработки:** `dev` (синхронизирована с `main` / `origin/main` на стартовом коммите). Вся разработка ведётся в `dev`; слияние `dev` в `main` выполняется только пользователем вручную.
- **Опора на встроенные возможности Bevy `0.20.0-dev`:**
  - `bevy_ecs` — отношения сущностей (`ChildOf`/`Children`, `Relationship`), реактивные наблюдатели (`Observer` / `On<E>`), lifecycle hooks, `hotpatching`;
  - `bevy_reflect` — единый реестр типов `AppTypeRegistry`, `reflect_auto_register`, `reflect_functions` для инспектора, сериализации и скриптинга;
  - `bevy_remote` — встроенный JSON-RPC сервер BRP (`RemotePlugin`, `RemoteHttpPlugin`), подписки `+watch` и экспорт схем типов (`registry.schema`);
  - `bevy_world_serialization` и `bevy_scene` — сериализация мира (`DynamicWorld`, `.scn.ron`) и композиционные шаблоны BSN (`Scene`, `Template`);
  - `bevy_render`, `bevy_pbr`, `bevy_sprite`, `bevy_camera`, `bevy_solari` — двухпоточный конвейер рендера, `RenderTarget::Image` + `GpuReadbackPlugin`, Forward/Deferred PBR, 2D-спрайты и `Text2d`, экспериментальные `meshlet` и `bevy_solari`;
  - `bevy_asset` — асинхронный `AssetServer`, `AssetProcessor`, `file_watcher`;
  - `bevy_animation`, `bevy_picking`, `bevy_gizmos`, `bevy_settings` — анимационные графы, 2D/3D picking, отладочные гизмо, TOML-настройки.

### Зафиксированные архитектурные решения

1. **Изоляция кода в `engine/`:** весь код движка, утилит сборки и редактора размещается в отдельной директории `engine/` рядом с существующими крейтами Bevy (`crates/bevy_*`). Сами крейты Bevy не модифицируются без острой необходимости, чтобы сохранять возможность обновления из upstream и не утяжелять компиляцию.
2. **Вьюпорт редактора — Вариант A (`ViewportTransport`):** единое окно Tauri + React + TypeScript со встроенным `<canvas>`-вьюпортом (offscreen-рендер Bevy в `RenderTarget::Image` + `GpuReadback` + локальный IPC-стрим кадров и пересылка ввода из UI) **плюс** кнопка открепления/прикрепления нативного окна Bevy (`Detach / Attach`) для работы с максимальным нативным FPS.
3. **Игровой скриптинг — Rhai:** 100% чистый Rust-рантайм `rhai` за абстракцией `ScriptBackend` в `engine_scripting` и мостом к ECS через `bevy_reflect` (`AppTypeRegistry` + `reflect_functions`), с последующей поддержкой визуального графа поверх того же рантайма.
4. **Физика и звук:**
   - физика строится внутри собственного фасада `engine_physics` поверх **`rapier3d`** и **`rapier2d`** (гарантированная совместимость с Bevy `0.20.0-dev` и единый ECS-подход для 2D и 3D);
   - звук строится сразу поверх **`kira`** за трейтом `AudioBackend` в `engine_audio` с заделом под добавление бэкенда **`firewheel`** для нодового DSP-графа (аналог MetaSounds).
5. **Кроссплатформенность и паритет 2D/3D:** архитектура ориентирована на Linux/Windows/macOS без жёсткой привязки к ОС-специфике (и с сохранением совместимости с будущим Web/WASM там, где возможно); **2D и 3D поддерживаются равнозначно с самого начала** (сцены, камеры, picking, гизмо, ассеты, физика, звук и шаблоны проектов).

### Учёт особенностей текущего репозитория и окружения

- **Правила `.gitignore`:** корневой `.gitignore` игнорирует `Cargo.lock` и `assets/**/*.meta`. При инициализации `engine/` необходимо завести собственный `engine/.gitignore`, который игнорирует `target/`, `node_modules/`, `dist/`, `.cache/` (DDC), но **не** игнорирует `.meta`-файлы ассетов движка и тестовых сэмплов (и явно определяет политику по `engine/Cargo.lock` для воспроизводимости сборок).
- **Независимый Cargo Workspace:** `engine/Cargo.toml` объявляется с собственной секцией `[workspace]`, чтобы `cargo check` / `cargo test` внутри `engine/` не запускали пересборку 62 крейтов, примеров и бенчмарков из корневого workspace Bevy, но при этом подключали локальные крейты из `../crates/bevy_*` по `path`.
- **Локальный тулчейн (проверено в окружении):** `rustc 1.96.0`, `cargo 1.96.0`, линкер `lld` (`/usr/bin/lld`), `clang`, `node v24.22.3`, `pnpm 12.21.0`, `cargo-tauri`, системные библиотеки `webkit2gtk-4.1`, `gtk+-3.0`, `gtk4`, `vulkan`, `wayland-client`, `x11`, `alsa`.

```text

├── .cargo/
│   └── config.toml                    # Настройки быстрой сборки (lld и др.) для локальной среды
├── crates/
│   ├── engine_core/                   # Ядро: App-обвязка, EntityGuid, WorldMode, ProjectManifest, EngineSet
│   ├── engine_protocol/               # Общие контракты IPC/BRP, типы ввода и бинарный протокол кадров вьюпорта
│   ├── engine_scene/                  # Сцены (.level.ron), префабы (.prefab.ron), 2D/3D пресеты, PIE snapshot
│   ├── engine_render/                 # Профили 2D/3D рендера, камеры, сетки, outline, ViewportTransport
│   ├── engine_assets/                 # Asset Registry, .meta/UUID, 2D/3D импортеры, DDC, миниатюры, .pak reader
│   ├── engine_input/                  # Enhanced Input: Actions, Axis1D/2D/3D, Mapping Contexts, Triggers
│   ├── engine_physics/                # Единый фасад физики: 3D (rapier3d) и 2D (rapier2d), FixedUpdate, debug
│   ├── engine_audio/                  # Фасад аудио: AudioBackend trait, бэкенд kira (и далее firewheel), шины
│   ├── engine_scripting/              # ScriptBackend trait, рантайм Rhai, Reflect-мост, hot-reload
│   ├── engine_editor_bridge/          # Плагин Engine Host: расширение BRP, WS IPC, picking, гизмо, Undo/Redo, PIE
│   ├── engine_build/                  # Граф зависимостей, cooking ассетов, сборка .pak, экспорт игр
│   ├── engine_runtime/                # Бинарник движка (--editor / --play / --headless)
│   └── engine_player/                 # Облегчённый релизный бинарник игры без редакторских зависимостей
├── editor/
│   ├── src-tauri/                     # Tauri v2 Rust-хост (менеджер проектов, запуск engine_runtime, ФС-диалоги)
│   └── ui/                            # React + TypeScript + Vite интерфейс редактора
├── samples/
│   ├── empty_project/                 # Минимальный пустой проект для smoke-тестов runtime
│   ├── sandbox_3d/                    # Демонстрационный 3D-проект (физика, свет, ввод, звук, Rhai)
│   └── sandbox_2d/                    # Демонстрационный 2D-проект (спрайты, физика 2D, камера, звук, Rhai)
└── templates/
    ├── template_2d/                   # Шаблон нового 2D-проекта
    ├── template_3d/                   # Шаблон нового 3D-проекта
    └── template_hybrid/               # Шаблон гибридного 2D/3D-проекта
```

### Краткое назначение ключевых модулей

- **`engine_core`**: определяет `EngineCorePlugin`, стабильный идентификатор `EntityGuid` (UUID v4/v7), режим мира `WorldMode` (`Mode2D`, `Mode3D`, `Hybrid`), манифест проекта `ProjectManifest` (`project.toml`), фиксированные наборы систем `EngineSet` (`Input`, `ScriptFixed`, `Physics`, `Gameplay`, `Audio`, `EditorSync`) и интеграцию пользовательских настроек через `bevy_settings`.
- **`engine_protocol`**: единые структуры команд/событий для Tauri, React UI и `engine_editor_bridge`, схема бинарного кадра offscreen-вьюпорта (`FrameHeader` + пиксели/сжатие) и событий пересылаемого ввода (`ForwardedInputEvent`).
- **`engine_scene`**: сериализация уровней (`.level.ron`) и префабов (`.prefab.ron`) поверх `bevy_world_serialization` с сохранением стабильных `EntityGuid` вместо эфемерных `Entity` ID, 2D/3D базовыми объектами и механизмом снятия/восстановления снимка мира для Play-In-Editor.
- **`engine_render`**: настройка 2D и 3D конвейеров рендера, редакторские камеры (3D orbit/fly и 2D pan/zoom), процедурные сетки (`Grid3D` / `Grid2D`), контур выделения, профили качества и абстракция `ViewportTransport` (единовременно поддерживающая offscreen `RenderTarget::Image` + `GpuReadback` для `<canvas>` и переключение в откреплённое нативное окно Bevy).
- **`engine_assets`**: управление `.meta`-файлами с `AssetUuid`, индексация в `AssetRegistry`, отслеживание зависимостей, импорт 3D (glTF/GLB, меши, PBR-материалы) и 2D (текстуры, `TextureAtlasLayout`, спрайты, `TilemapAsset`), локальный DDC на базе `bevy_asset::AssetProcessor`, генерация миниатюр и чтение упакованных `.pak`-архивов.
- **`engine_input`**: декларативные действия `InputAction`, оси (`Bool`, `Axis1D`, `Axis2D`, `Axis3D`), приоритетные контексты `InputMappingContext`, триггеры (`Pressed`, `Released`, `Hold`, `Tap`, `Chord`) и модификаторы (`Deadzone`, `Scale`, `Invert`, `Swizzle`) с сохранением пользовательских привязок.
- **`engine_physics`**: общий слой типов (`PhysicsMaterial`, `CollisionLayers`, `TriggerEvent`, `CollisionEvent`, `FixedTransform` с интерполяцией) и два равноправных бэкенда — `rapier3d` и `rapier2d`, включая raycast/shapecast, суставы, контроллеры персонажа 2D/3D и визуализацию через `bevy_gizmos`.
- **`engine_audio`**: абстракция `AudioBackend`, стартовый бэкенд на `kira` (шины `Master`/`SFX`/`Music`/`UI`/`Voice`, фильтры и эффекты шин, 2D/3D пространственное затухание, пул источников, стриминг длинных треков), к которому на позднем этапе добавляется бэкенд `firewheel`.
- **`engine_scripting`**: абстракция `ScriptBackend`, реализация на `rhai` с лимитами памяти/операций (песочница), `ScriptComponent` с параметрами для инспектора, автоматический доступ к отражённым компонентам через `AppTypeRegistry` и горячая перезагрузка `.rhai`-скриптов.
- **`engine_editor_bridge`**: соединяет Engine Host и редактор — расширяет `bevy_remote`, поднимает WebSocket IPC для стрима кадров, ввода и событий в реальном времени, реализует 2D/3D picking, 2D/3D гизмо трансформации, транзакционный стек Undo/Redo и управление PIE.
- **`engine_build`, `engine_runtime`, `engine_player`**: разделение среды разработки (`engine_runtime` со всеми редакторскими мостами) и чистого клиентского бинарника (`engine_player`) плюс автоматизированный экспорт игр (`engine_build`).

## 3. Поэтапный план разработки (Этапы 0–10)

### Этап 0 — Инициализация workspace `engine/` и базовый runtime

- **Цель:** развернуть изолированный Cargo workspace внутри `engine/`, зафиксировать базовые типы ядра и получить рабочий исполняемый файл `engine_runtime`, собирающийся и проходящий проверки поверх локального Bevy `0.20.0-dev`.
- **Результат:** компилируемый workspace `engine/` с крейтами `engine_core` и `engine_runtime`, способный запускаться в `--headless` и `--window` режимах и читать `project.toml` из `engine/samples/empty_project`.
- **Зависимости:** нет (опора на существующие крейты в `crates/bevy_*`).
- **Задачи:**
  - `0.1` **Инициализация workspace и правил репозитория для `engine/`:** создать `engine/Cargo.toml` (независимый `[workspace]`, `edition = "2024"`, зависимости на `../crates/bevy_*`), `engine/.gitignore` (исключение `target/`, `node_modules/`, `dist/`, `.cache/` с явным сохранением `.meta` в `engine/`) и при необходимости локальный профиль быстрой сборки с `lld` и опцией `dynamic_linking`.
  - `0.2` **Крейт `engine_core`:** реализовать `EngineCorePlugin`, компонент `EntityGuid` (стабильный UUID + индекс быстрого поиска `EntityGuidMap`), ресурс `WorldMode` (`Mode2D` / `Mode3D` / `Hybrid`), парсер и валидатор манифеста проекта `ProjectManifest` (`project.toml`), фиксированные наборы расписаний `EngineSet` и регистрацию типов в `AppTypeRegistry`.
  - `0.3` **Крейт `engine_runtime` и тестовый проект `empty_project`:** реализовать CLI-параметры (`--project`, `--headless`, `--window`, `--editor`), инициализацию `App` с `DefaultPlugins` (или `MinimalPlugins` в headless-режиме), загрузкой `project.toml` и созданием минимального проекта `engine/samples/empty_project`.
- **Критерии готовности (DoD):**
  - `engine/` собирается без изменения корневого `Cargo.toml` и крейтов в `crates/bevy_*`.
  - `ProjectManifest` корректно загружается, валидируется и покрыт unit-тестами; `EntityGuid` гарантирует уникальность и маппинг `UUID <-> Entity`.
  - `engine_runtime --headless --project samples/empty_project` стартует, проходит N кадров без ошибок и корректно завершается.
- **Способ проверки:**
  - `cargo check --manifest-path engine/Cargo.toml --workspace`
  - `cargo clippy --manifest-path engine/Cargo.toml --workspace --all-targets -- -D warnings`
  - `cargo test --manifest-path engine/Cargo.toml -p engine_core`
  - `cargo run --manifest-path engine/Cargo.toml -p engine_runtime -- --headless --project engine/samples/empty_project --max-frames 5`

### Этап 1 — Протокол, сериализация 2D/3D сцен и `ViewportTransport` (Вариант A)

- **Цель:** обеспечить полноценный цикл работы Engine Host: сериализацию 2D и 3D сцен, двухрежимный рендер вьюпорта (offscreen `<canvas>` и открепляемое нативное окно) и сетевой/IPC протокол управления миром.
- **Результат:** `engine_runtime --editor` поднимает BRP + WebSocket IPC, загружает/сохраняет `.level.ron` для 2D и 3D сцен и стримит кадры через `ViewportTransport`.
- **Зависимости:** Этап 0.
- **Задачи:**
  - `1.1` **Крейт `engine_protocol`:** определить версионированные структуры запросов/ответов редактора, событий мира (иерархия, выделение, логи, метрики FPS/кадра), формат бинарного фрейма вьюпорта (`width`, `height`, `format`, `frame_id`, буфер RGBA/сжатый кадр) и события ввода (`PointerMove`, `PointerButton`, `Wheel`, `Key`, `Resize`, `SetViewportMode`).
  - `1.2` **Крейт `engine_scene` и стартовые сэмплы 2D/3D:** реализовать сохранение и загрузку уровней `.level.ron` поверх `bevy_world_serialization` с сохранением `EntityGuid`, `Name`, `Transform`, `Visibility`, `ChildOf`/`Children` и версионированием формата; добавить фабрики 2D/3D примитивов (`Sprite`, `Camera2d`, `Mesh3d` куб/сфера/плоскость, `DirectionalLight`/`PointLight`, `Camera3d`) и минимальные сцены в `engine/samples/sandbox_3d` и `engine/samples/sandbox_2d`.
  - `1.3` **Крейт `engine_render` и `ViewportTransport`:** реализовать редакторские камеры (3D orbit/fly и 2D pan/zoom с переключением режима), процедурные сетки (`Grid3D` и `Grid2D`), профили камеры/фона и двойной транспорт вывода:
    - режим `Offscreen`: рендер в `RenderTarget::Image` с чтением через `GpuReadbackPlugin` и адаптивным троттлингом/ресайзом под размер панели UI;
    - режим `NativeWindow`: показ/скрытие нативного окна Bevy с тем же состоянием редакторской камеры (`Detach / Attach`).
  - `1.4` **Крейт `engine_editor_bridge`:** подключить `RemotePlugin` / `RemoteHttpPlugin` (BRP) с `registry.schema`, добавить кастомные BRP-методы (`engine.scene.load`, `engine.scene.save`, `engine.scene.new`, `engine.world.tree`, `engine.entity.spawn_preset`, `engine.viewport.set_mode`), поднять WebSocket IPC-сервер для высокочастотного обмена (кадры вьюпорта, пересланный ввод, поток логов и событий изменений).
- **Критерии готовности (DoD):**
  - Сцена 2D и сцена 3D сохраняются в `.level.ron`, перезагружаются в чистый `World` с сохранением всех `EntityGuid`, иерархии `ChildOf` и компонентов.
  - Offscreen-рендер формирует непустые буферы кадров в `RGBA8` для 2D и 3D сцен без падений при изменении разрешения.
  - Протокол переключения `Offscreen <-> NativeWindow` меняет режим работы вьюпорта без потери сцены и позиции камеры.
- **Способ проверки:**
  - `cargo test --manifest-path engine/Cargo.toml -p engine_protocol -p engine_scene -p engine_render -p engine_editor_bridge`
  - Интеграционный headless-тест round-trip загрузки/сохранения сцен `sandbox_3d` и `sandbox_2d` с проверкой совпадения `EntityGuid` и иерархии.
  - Smoke-тест `engine_runtime --editor` с проверкой JSON-RPC запросов `registry.schema` и `engine.world.tree` и получением тестового кадра по WebSocket.

### Этап 2 — MVP редактора на Tauri + React + TypeScript

- **Цель:** создать оболочку редактора на Tauri + React + TypeScript, подключённую к `engine_runtime --editor`, со встроенным `<canvas>`-вьюпортом, инспектором по рефлексии, деревом сцены и сохранением уровней.
- **Результат:** запускаемое десктопное приложение редактора с рабочим 2D/3D вьюпортом, World Outliner, Reflected Inspector, Console и Load/Save сцен.
- **Зависимости:** Этап 1.
- **Задачи:**
  - `2.1` **Каркас `engine/editor` (Tauri v2 + React + TS + Vite):** настроить `engine/editor/src-tauri` и `engine/editor/ui` (`pnpm`), реализовать в Tauri-бэкенде супервизор процесса `engine_runtime --editor` (запуск с выбранным проектом, проверка готовности портов, корректное завершение при выходе, перезапуск при падении), нативные диалоги открытия/сохранения и чтение метаданных проекта.
  - `2.2` **TS-клиент протокола и докинг-лейаут:** реализовать типизированный клиент BRP + WebSocket в `editor/ui`, базовую систему панелей (докинг/сплиты с сохранением раскладки в `localStorage`), верхний тулбар (`New/Open/Save Scene`, переключатель `2D / 3D`, статус подключения к Engine Host).
  - `2.3` **Панель Viewport (`<canvas>` + `Detach / Attach`):** реализовать рендер бинарного потока кадров из WebSocket на `<canvas>` (через `ImageData` / `WebGL2` текстуру с минимальной задержкой), автоматическую отправку `ResizeObserver` размеров, захват и пересылку событий мыши/колеса/клавиатуры для навигации 3D orbit/fly и 2D pan/zoom, а также кнопку `Detach / Attach` для переключения в нативное окно Bevy и обратно.
  - `2.4` **Панели `World Outliner` и `Console`:** отобразить иерархическое дерево сущностей (с поиском, видимостью, созданием пустых сущностей и 2D/3D пресетов, удалением, переименованием, drag-and-drop изменением родителя) и консоль логов Engine Host с фильтрацией по уровням (`INFO`/`WARN`/`ERROR`).

### Этап 6 — Play-In-Editor (PIE) и скриптинг на Rhai

- **Цель:** объединить все подсистемы в единый цикл создания игр прямо в редакторе — запускать сцену в режиме игры, откатывать её обратно и писать игровую логику на Rhai с горячей перезагрузкой.
- **Результат:** кнопка `Play / Pause / Step / Stop` в редакторе и полноценная система скриптинга на Rhai с доступом к ECS, физике, вводу, звуку и спавну префабов.
- **Зависимости:** Этап 5.
- **Задачи:**
  - `6.1` **Режим Play-In-Editor (PIE):** реализовать в `engine_editor_bridge` и `engine_scene` жизненный цикл `Edit -> Play -> Pause -> Step -> Stop`: снятие полного снимка сцены перед стартом симуляции, активация игровых систем (`Physics`, `Audio`, `Gameplay`, `Scripting`, игровой контекст `engine_input`, переключение на активную игровую камеру), блокировка/индикация изменений во время PIE и гарантированный откат мира к исходному снимку по нажатию `Stop`.
  - `6.2` **Крейт `engine_scripting` — `ScriptBackend` и рантайм Rhai:** спроектировать абстракцию `ScriptBackend`, реализовать `RhaiBackend` с настройкой песочницы (`max_operations`, лимиты стека/аллокаций для защиты от бесконечных циклов), кэшем скомпилированных AST и компонентом `ScriptComponent` (ссылка на `.rhai`-ассет + карта публичных сериализуемых свойств `ScriptProperties`, отображаемая и редактируемая в Inspector).

- **Критерии готовности (DoD):**
  - Вход в PIE и выход по `Stop` 10 раз подряд не оставляют «мусорных» сущностей и полностью восстанавливают исходные координаты и компоненты сцены.

### Этап 8 — Инструменты авторов контента (2D Tilemap/Sprites, 3D Animation, Material Graph, Profiler)

- **Цель:** приблизить рабочие процессы создания контента к стандартам современных редакторов (Unreal / Godot / Unity) как в 2D, так и в 3D.
- **Результат:** встроенные инструменты для 2D тайлмапов и покадровых анимаций, 3D графов анимации, визуального редактора материалов (WESL) и профилирования производительности.
- **Зависимости:** Этап 7.
- **Задачи:**
  - `8.1` **Инструменты 2D-контента (`Tilemap` + `Sprite Animation`):** реализовать в `engine_render`/`engine_scene`/`editor/ui` редактор `Tilemap` (слои тайлов, кисть/заливка/ластик/прямоугольник, авто-генерация коллайдеров `rapier2d` по слоям) и редактор 2D покадровых клипов анимации на базе `TextureAtlasLayout` со стейт-машиной переходов.
  - `8.2` **Инструменты 3D-анимации (`bevy_animation`):** добавить в редактор просмотрщик иерархии костей/скелетов, инспектор `AnimationClip` и визуальный редактор `AnimationGraph` (состояния, blend-узлы, таймлайн событий анимации `AnimationEvent` с привязкой к звуку и Rhai-хукам).
  - `8.3` **Нодовый `Material Graph` -> WESL:** реализовать в React/TS визуальный редактор узлов материала (PBR-выходы `BaseColor`/`Roughness`/`Metallic`/`Normal`/`Emissive` для 3D и Sprite/Unlit/Mask выходы для 2D, текстурные семплеры, математика, UV, время), компилятор графа в чистый `WESL`-шейдер и динамическую регистрацию `ExtendedMaterial`/`Material2d` с live-превью.
  - `8.4` **Профилировщик и графические профили:** реализовать в редакторе панель `Profiler` (время систем, Main/Render thread frame time, число draw calls, сущностей, память ассетов через `bevy_diagnostic`/`schedule_data`) и настраиваемые графические пресеты (`Low`/`Medium`/`High`/`Ultra`: тени, TAA/SMAA, SSAO, SSR, Bloom, Volumetric Fog, режимы отладки вьюпорта `Unlit`/`Wireframe`/`Normals`/`Depth`).
- **Критерии готовности (DoD):**
  - В 2D-сцене можно нарисовать тайлмап, настроить коллизию и проиграть спрайт-анимацию в PIE.
  - В 3D-сцене проигрывается `AnimationGraph` с переходами между клипами и срабатыванием событий на ключевых кадрах.
  - Граф материала компилируется в валидный WESL-шейдер без ошибок `wgpu` и обновляет объект во вьюпорте в реальном времени.
- **Способ проверки:**
  - Unit-тесты кодогенерации `Material Graph -> WESL` (валидация графов, обнаружение циклов, проверка сгенерированного кода).
  - Тесты загрузки и автогенерации коллайдеров тайлмапов; тесты трансляции `AnimationGraph`.
- **[Контрольная точка тестирования №7]:** ручная проверка пользователем рисования тайлмапа, настройки материала через нодовый граф, 3D/2D анимаций и панели профайлера.

### Этап 9 — Расширяемость, визуальный скриптинг и DSP-граф звука (`firewheel`)

- **Цель:** открыть архитектуру движка для сторонних расширений, добавить визуальный скриптинг (ориентир Blueprints) поверх Rhai и вывести аудио-систему на уровень нодового DSP-графа (ориентир MetaSounds).
- **Результат:** SDK плагинов движка и UI, редактор визуального скриптинга (компилируемый в Rhai) и бэкенд `firewheel` в `engine_audio`.
- **Зависимости:** Этап 8.
- **Задачи:**
  - `9.1` **SDK расширения движка и UI:** оформить публичный контракт `EnginePlugin` (регистрация компонентов/систем, кастомных импортёров ассетов, BRP-методов и функций для Rhai), механизм подключения расширений из игровых проектов (`rust_game/` Cargo-крейт проекта), а также API регистрации кастомных вкладок и инспектор-виджетов в React UI на базе JSON Schema; создать эталонный пример плагина.
  - `9.2` **Визуальный скриптинг (Node Graph -> Rhai):** реализовать в React редактор потоковых и событийных графов (`OnStart`, `OnUpdate`, ветвления, циклы, переменные, вызовы физики/звука/анимации), компилирующий граф в читаемый `.rhai`-файл с маппингом узлов на строки для подсветки ошибок и отладки.
  - `9.3` **Бэкенд `firewheel` и нодовый аудио-граф в `engine_audio`:** реализовать `FirewheelAudioBackend` за существующим трейтом `AudioBackend`, добавить граф DSP-узлов (генераторы, микшеры, фильтры, delay/reverb, рандомизаторы, параметры от геймплея), редактор аудио-графа в UI, реверберационные зоны (Reverb Volumes) и простую окклюзию звука через физические лучи.
- **Критерии готовности (DoD):**
  - Внешний игровой плагин на Rust добавляет свой компонент и кастомную панель редактора без модификации ядра движка.
  - Визуальный граф компилируется в рабочий `.rhai` и выполняет игровую логику в PIE так же, как текстовый скрипт.
  - `engine_audio` переключается между `kira` и `firewheel` через конфигурацию, а параметры из игры в реальном времени модулируют DSP-граф.
- **Способ проверки:**
  - Тесты транспиляции визуального графа в Rhai (проверка корректности AST и выполнения тестовых графов в `engine_scripting`).
  - Интеграционный тест подключения примерного внешнего `EnginePlugin` к `engine_runtime` и `engine_player`.
  - Тесты построения и расчёта DSP-графа `firewheel` (включая headless аудио-буферный тест).
- **[Контрольная точка тестирования №8]:** ручная проверка пользователем сборки мини-логики на визуальном графе, звукового DSP-графа и подключения пользовательского плагина.

### Этап 10 — Долгосрочный AAA/Unreal-вектор

- **Цель:** последовательно наращивать высокоуровневые возможности движка, приближающие его к возможностям Unreal Engine в части графики, больших миров, ИИ, VFX и сети.
- **Результат:** модульный набор продвинутых подсистем, подключаемых по мере готовности и необходимости проектов.
- **Зависимости:** Этап 9 (подзадачи внутри этапа могут выполняться итеративно в выбранном пользователем приоритете).
- **Задачи:**
  - `10.1` **VFX / GPU-частицы (ориентир Niagara) и 2D-освещение:** система эмиттеров и модулей частиц на GPU (compute-буферы в `bevy_render`) с кривыми по времени жизни, столкновениями и редактором эффектов; для 2D — система 2D-светильников, карт нормалей и мягких 2D-теней.
  - `10.2` **Навигация и ИИ (2D и 3D):** генерация NavMesh (для 3D-геометрии и 2D-тайлмапов/полигонов), поиск пути A*/crowd avoidance и базовый фреймворк State Tree / Behavior Tree с отладчиком активных состояний в PIE.
  - `10.3` **Большие миры, ландшафт и фолиаж:** поддержка под-уровней (`Sublevels`), пространственная сетка стриминга (ориентир World Partition), сдвиг начала координат (Floating Origin), редактор ландшафта на картах высот (`Terrain` + кисти скульптинга/покраски слоёв + `Heightfield` в `rapier3d`) и инстансинг растительности (Foliage).
  - `10.4` **Next-gen рендеринг, zero-copy viewport и сеть:** интеграция экспериментальных `bevy_pbr::experimental::meshlet` (ориентир Nanite) и `bevy_solari` (ориентир Lumen) как профилей рендера на поддерживаемом железе; апгрейд `ViewportTransport` до zero-copy GPU texture sharing (DMABUF / DXGI Shared Handle / IOSurface) при сохранении offscreen fallback; подсистема сетевой репликации `engine_net` (client/server, снапшоты состояния, RPC, prediction).
- **Критерии готовности (DoD):**
  - Каждая подсистема этапа имеет изолированный крейт/плагин, ассет-формат с `.meta`/UUID, редакторскую визуализацию/инспектор и включается через `ProjectManifest`.
  - Введение фич Этапа 10 не ломает базовые 2D/3D проекты и сборку `engine_player`.
- **Способ проверки:**
  - Выделенные бенчмарки производительности (число частиц, скорость генерации NavMesh, стриминг чанков мира, время кадра с `meshlet`/`solari`) и интеграционные тесты каждой подсистемы.

## 4. Регламент выполнения на Этапе 3

1. **Ветвление:** вся разработка ведётся исключительно в ветке `dev`. Слияние `dev` в `main` никогда не выполняется автоматически — его делает только пользователь.
2. **Проверка состояния перед работой:** перед началом каждой задачи проверяются `git status` и текущая ветка (`dev`).
3. **Малые итеративные шаги:** задачи (`0.1`, `0.2`, ...) выполняются строго по порядку. После каждого завершённого изменения:
   - даётся краткое описание того, что именно изменено;
   - запускаются профильные проверки (`cargo check`, `cargo clippy -- -D warnings`, `cargo test`, а для UI — `pnpm typecheck`, `pnpm build` и тесты);
   - оформляется один осмысленный commit в `dev` и выполняется `git push origin dev`;
   - сообщается хеш коммита и результат `push`.
4. **Контрольные точки тестирования:** после завершения соответствующих этапов (см. контрольные точки №1–№8) разработка приостанавливается, подробно описывается готовая функциональность и шаги для ручной проверки пользователем. Продолжение по плану происходит после получения результатов тестов и исправления выявленных проблем.
